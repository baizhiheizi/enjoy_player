# UI Contract: Settings Section/Row Registry

**Consumers**: `SettingsLayoutSingleColumn`, `SettingsLayoutTwoPane` (rail), `SettingsSearchField` (index), `SettingsCollapsibleSection` (default-collapse state).

## Contract

1. There is exactly **one** static list of `SettingsSearchEntry` (see [data-model.md](../data-model.md)) that every consumer above reads from. No consumer may maintain its own hard-coded copy of section/row titles or ids.
   - *(Amended 2026-09, issue #754: the title/id **order** consumers render in derives from this registry — both layouts walk `kSettingsRegistry`'s section headers through `visibleSettingsSections()` (`lib/features/settings/presentation/settings_section_spec.dart`), so the rail, the single-column stack, the collapse seed, and the search index cannot disagree on membership or order. Rendering details (icon, l10n title/hint/keywords accessors, visibility predicate, body builder, card/collapse shape) live in the presentation-layer `SettingsSectionSpec` list, which is keyed to this registry by `sectionId` and drift-checked against it (`test/features/settings/presentation/settings_section_registry_drift_test.dart`). The spec list is data, not a second source of truth: a spec without a registry header, a header without a spec, or a row present in only one of the two is a contract violation.)*
2. Every row currently rendered by `SettingsScreen` (Cloud sync, Appearance & Language ×3 rows, AI providers, Recording, Keyboard shortcuts ×2 rows, Developer ×3 rows, About) MUST have exactly one registry entry. Adding a row to a section in code without adding its registry entry is a contract violation (caught by the widget test described in [quickstart.md](../quickstart.md)). *(Amended 2026-09: Account removed from the mandatory list — account management moved to the Profile tab, so the Settings hub no longer renders an Account section; see [docs/features/settings.md](../../../docs/features/settings.md).)*
3. A registry entry's `title` is resolved through `AppLocalizations` at read time — the registry never hard-codes an English string, so it stays correct across locale switches without a rebuild of the registry itself. *(Amended 2026-09, issue #754: resolution happens through the spec's `String Function(AppLocalizations)` accessors — `localizedSettingsRegistry(l10n)` looks each descriptor up in its section's `SettingsSectionSpec` — replacing the old `application/settings_registry_localizer.dart` switch. The domain registry itself still contains no strings at all.)*
4. Conditional visibility (desktop-only keyboard shortcuts, debug-only developer tools) is carried **by each section's `SettingsSectionSpec.isVisible` predicate** and applied **once** by `visibleSettingsSections()`, which both layouts and the two-pane rail read. *(Reversed 2026-09, issue #754: previously this contract required visibility to be applied per-consumer "by the rendering widget", leaving the registry platform-agnostic and each layout to hand-copy the same predicates — the single-column if-chain and the two-pane `_railSectionIds()` were separate sync points over the same ids. The reversal keeps one guarantee and trades another:)*
   - The **domain** registry (`kSettingsRegistry`) stays platform/state-agnostic — it still lists Keyboard shortcuts and Developer unconditionally, and rows it lists unconditionally must never be *rendered* as search results or rail items on a build where their section is gated off.
   - The **presentation** spec registry is deliberately platform-aware: the same `isDesktop` / `!kReleaseMode` predicates (FR-005/FR-006 — no new gating logic, just expressed exactly once) live on the specs, so both layouts and the rail produce identical visible-section sets **by construction** instead of by convention. The drift test asserts spec coverage so a section cannot be added on one side only.
5. `sectionId` and `rowId` values are stable identifiers (not display strings) and MUST NOT change once introduced, since they may be referenced by `settingsSelectedSectionProvider` / `settingsSectionCollapseProvider` state that could theoretically outlive a single build (e.g. via widget rebuilds during a session).

## Non-goals

- This registry does not gate whether a *feature* exists (e.g. it doesn't decide whether AI providers are BYOK-capable) — it only describes what's discoverable in the Settings hub's IA. Feature-level capability logic stays exactly where it lives today.
